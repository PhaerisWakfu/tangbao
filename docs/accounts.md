# 账号、匿名体验、旧口令与 Resend 方案

状态：设计，尚未实现。日期：2026-11-03。用户确认的产品范围由 [账号 Epic](https://github.com/PhaerisWakfu/tangbao/issues/5) 维护；实施前的未决项列在本文末尾。本文没有执行生产迁移、开通 Resend、配置 DNS 或发送邮件。

## 已确认的产品规则

1. 申请成为 AI 前必须注册账号，以便将运营者发言及管理行为关联到可管理的身份。
2. 聊天访客允许匿名体验一个对话，发起第二个对话时要求注册。
3. 登录采用“邮箱 + 密码”。邮箱验证码用于验证邮箱和账号/密码找回，不在每次登录时发送，以控制发送量。

下文关于状态、数据结构、迁移、安全和额度数字是实施建议，不应与上述产品决定混淆。

## 哪些人需要账号

| 身份/场景 | 账号要求 | 建议行为 |
| --- | --- | --- |
| 第一次体验的聊天访客 | 可匿名 | 创建并继续同一段对话；沿用文字/图片和发送限流 |
| 想发起第二段对话的人 | 必须注册 | 注册并验证邮箱后继续草稿；不是每发一条消息都注册 |
| 新 AI 申请者 | 必须注册并验证邮箱 | 使用账号发起申请，审批通过后获得模型运营资格 |
| 已有模型运营者 | 过渡期绑定新账号 | 先证明掌握旧口令，再绑定已验证的新账号 |
| 管理员 | 独立账号与显式管理角色 | 通过受控引导建立首个管理员；公开注册不授予管理权限 |

同一个人可以用一个账号聊天并经营模型。账号停用与模型停用是两项操作：前者影响账号的所有会话，后者影响某个模型接单/回复。是否允许停用运营者以普通用户身份继续聊天，由后台策略明确决定。

建议未验证账号只获得验证/找回所需的受限会话，完成验证后才能新建第二段对话或提交 AI 申请；具体门槛在实施前定案。验证邮箱证明的是邮箱控制权，不等于实名、发言可追责到自然人或内容安全保证。

## 一次匿名体验怎么执行

推荐采用“渐进注册”：首页可浏览、第一段可聊，第二段出现注册入口。第二段拦截须在创建接口执行，不能只禁用“新对话”按钮。

1. 服务端生成高熵匿名身份，用 HttpOnly/Secure/SameSite cookie 关联 `guest_identities`，不以可自填的 `x-visitor` 作为额度凭证。
2. 创建首段时，用同一 DB 原子单元条件消耗 `created_count < 1` 并创建对话，成功后将该匿名身份标为已使用。并发、超时重试、接口直调均遵守相同规则；配合请求幂等键防重复创建。
3. 同一段可继续发消息；删除对话不恢复额度。第二次创建返回稳定的 `AUTH_REQUIRED` 错误码和注册入口，不创建空对话、不上传无人归属的图片。
4. 前端在本次页面内保留草稿及附件，使用弹层完成注册后重试。若必须跳转，附件需明确的临时存储/恢复与清理方案，不能只保存已经失效的 object URL。
5. 注册后由用户选择关联原匿名对话，服务端同时验证登录身份和该对话原凭证，防止只凭同一 IP 或 visitor ID 批量归集历史。完成绑定后以账号授权并撤销/轮换旧匿名访问凭据，明确历史访问兼容策略。
6. 既有多段匿名历史不删除，凭原 token 仍可读和继续；下一次新建时引导注册。上线时需明确旧标识到新匿名身份的映射及已使用额度初始化，不能直接伪造一个“历史精确计数”。

匿名限制只能约束一个服务端匿名身份。清 Cookie、隐私模式、换浏览器会产生新身份；IP 限流/风险挑战可抑制滥用，但不能严禁共享网络，也不能宣称严格“一人一次”。账号上线后原发送和全站排队限制仍然生效，注册不是无限资源通行证。

## 账号和数据结构

保留现有对话/消息，不把模型号直接作为账号主键。建议新增或扩展：

| 表/字段 | 核心内容与约束 |
| --- | --- |
| `accounts` | 随机稳定 ID、规范化邮箱 unique、password hash/版本、邮箱验证时间、状态、创建/修改时间 |
| `account_roles` | account_id + role unique；user/operator/admin 的授予来源和时间 |
| `operators.operator_uid` | 不变的内部身份 unique；保留原 `id` 作为兼容型号，逐步迁移引用 |
| `operators.owner_account_id` | 已认领账号；仅一个 owner，认领通过条件写保证唯一 |
| `applications.account_id` | 新申请归属；同账号的待审批/已通过重复策略受数据库约束 |
| `threads.account_id` / `guest_identity_id` | 账号或匿名归属；旧 bearer token 在迁移前继续按旧规则校验 |
| `guest_identities` / 请求幂等表 | 额度消耗、首段关联、创建请求结果；删除对话不删额度事实 |
| `account_sessions` | 随机 session 的摘要、账号、权限版本、到期及撤销时间；客户端不携带可信角色声明 |
| `email_challenges` | purpose、账号/邮箱、challenge ID、验证码 HMAC、到期、失败次数、消费/撤销时间 |
| `legacy_claims` | 模型归属证明、目标账号、一次性凭据摘要、到期、消费时间与审计事件 |
| `mail_deliveries` | challenge 对应幂等发送任务、供应商 ID、状态、尝试次数、重试时间和去重事件 ID |

这是逻辑草案，不是可直接上线的 SQL。D1 batch 与 Turso transaction 必须逐项确认原子性、条件写返回值和并发冲突处理。账号身份、型号和角色变更不能依赖更新所有历史行才能维持授权。

邮箱规范化：去前后空白、明确大小写和国际化域名政策；不按供应商规则删除 `+tag` 或点号，防止错误合并不同地址。唯一性由数据库保障，不只在注册前查询。密码不 trim、不静默截断，允许粘贴和密码管理器；建议 15–128 字符并限制请求体，登录限流先于昂贵 KDF。

密码采用经审查的自适应加盐 KDF，优先评估 Argon2id，在 Worker CPU/内存预算中做基准再决定实现及参数；若不满足预算，应评审受支持的替代方案或专用身份服务，不能静默降为一次 SHA-256。存储包含算法、版本、参数和随机 salt，便于升级。不要假设 Node 的原生扩展能在 Worker 运行。参见 [OWASP 密码存储指南](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html) 和 [Workers crypto 支持边界](https://developers.cloudflare.com/workers/runtime-apis/nodejs/crypto/)。

## 旧口令如何绑定

旧口令是原模型的归属证明，不是新账号密码，不能将所有旧账号批量变成同一邮箱密码。

推荐流程：注册新账号并验证邮箱 → 登录 → “绑定已有模型” → 输入旧口令 → 服务端校验旧凭据并展示目标型号 → 确认绑定 → 原子写入 owner 并消费认领凭据 → 撤销旧口令登录能力及相关旧会话 → 继续使用原模型和历史对话。

关键约束：

- 认领请求必须绑定当前 account_id、目标 operator_uid、用途和有效期；用短期一次性凭据，最后提交时重新校验账号/邮箱状态与模型未被认领。整个请求限流并检查来源/CSRF。
- 只校验一次后在浏览器塞个型号不构成证明；失败、重复提交和两个账号竞争时，最多一个账号成为 owner，另一个收到明确冲突。
- 不按历史申请邮箱自动分配模型；该邮箱没有经过验证。申请记录缺失、邮箱重复、旧口令共享/遗失、已停用模型等进入人工核验清单，不能采取先到先得认领。
- 已停用模型不因成功绑定自动恢复；争议模型暂停自动认领。多个模型如何归同一账号要有显式政策，不能用“邮箱相同”默默合并。
- 管理员和主模型单独迁移：通过受控后台/部署操作将首个管理员绑定到已验证账号；不要让公开旧口令认领接口授予 admin。保留限时、可审计的应急恢复方式。
- 过渡期新旧登录并行但已认领模型禁用旧登录。旧签名 cookie 还可能存活，所以旧 `requireSeat` 也必须检查认领/撤销状态，单改登录接口不够。
- 型号、对话分配、推送订阅、历史审批关联及停用状态都需保留。改型号不能改变 account_id 或“借用”旧型号重新获得历史权限。

建议上线分四步：新增表字段及可回退代码 → 邀请少量受控账号演练 → 在明确期限内开放认领并统计未绑定项 → 确认残留与恢复渠道后退役旧登录。任何清理旧凭据或真实数据的不可逆步骤都需单独说明范围、备份、恢复及授权；本轮没有执行这些操作。

## 邮箱验证与密码找回

建议验证码 6 位、10 分钟有效、每个 challenge 最多 5 次失败；重发间隔 60 秒，每邮箱每小时建议不超过 5 次，并有账号/IP/全站日预算。上述数字是初始建议，按实际使用量调整，不是 Resend 套餐上限。

- 验证和找回必须是不同 purpose，验证码绑定邮箱和 challenge。数据库存带服务端 pepper 的 HMAC，避免低熵验证码仅存普通摘要后被离线穷举。
- 随机数必须来自加密安全源；校验、计数、消费用原子条件写，成功只能消费一次。重发后旧验证码失效，过期和超限可重新申请。
- 验证邮箱不直接提升管理角色。普通登录只做密码校验和发 session，不发送邮件。
- 忘记密码入口对存在/不存在邮箱返回统一提示，抑制账号枚举；验证成功只发短期、单用途的重置凭据，不返回密码，也不将验证码当长期 session。
- 设置新密码和消费重置凭据在同一原子单元完成，撤销全部旧 session，再要求正常登录。修改绑定邮箱需要当前认证、验证新邮箱和旧会话处理，另建独立需求，不能靠未认证找回接口改邮箱。

## Resend 具体怎么接

当前项目没有 Resend 集成。Resend 负责送邮件，本项目负责生成/校验验证码、账号状态和密码找回。可直接使用 Worker 的 `fetch` 调用邮件 API，无需为了邮件模板引入 React。

1. 选择由站点运营方控制的事务邮件子域名，例如 `account.example.com`，在 Resend 添加并验证；按其控制台给出的 DNS 记录配置 SPF/DKIM，按需加 DMARC。生产收件人发送前完成域名验证，具体记录值不能照抄示例。参见 [域名说明](https://resend.com/docs/dashboard/domains/introduction)。
2. 创建仅用于发送、尽可能限定域名的 API key。使用 Worker secret `RESEND_API_KEY`；普通配置 `MAIL_FROM`、`APP_ORIGIN`、`MAIL_MODE`。需要回调时增加 secret `RESEND_WEBHOOK_SECRET`。密钥不放浏览器或 Git。
3. 新增后端邮件服务，如 `src/email.ts`，接收已校验的收件人、验证码、用途和 challenge ID。模板使用简洁中文、站点名、用途、有效期、“非本人操作可忽略”，不包含旧口令或用户消息。
4. `POST https://api.resend.com/emails`，请求头为 `Authorization: Bearer <secret>`、`Content-Type: application/json`、`Idempotency-Key: email-verify/<challenge-id>`；body 为 `from`、`to`、`subject`、`text`，需要时加安全生成的 `html`。找回用另一用途前缀。API 参数参见 [发送邮件](https://resend.com/docs/api-reference/emails/send-email)。
5. 同一个 challenge 重试必须复用相同正文和幂等键；Resend 当前幂等键保留 24 小时，本地另存长期任务状态，不把供应商窗口当作永久去重。[幂等说明](https://resend.com/docs/dashboard/emails/idempotency-keys)。
6. 持久化 outbox 后同步等待一次发送结果，或由专用队列消费；`ctx.waitUntil` 本身不是持久化重试队列。429/临时 5xx 指数退避、有次数上限并遵守 Retry-After；永久参数/域名/权限错误不无限重试。重发冷却和预算在调用 Resend 前原子扣减。
7. 为了重试同一封包含验证码的邮件，outbox 的短期 payload 要用独立密钥加密并在到期后清除，不在任务表明文长期保存验证码；验证表仍只保存 HMAC。
8. API 返回邮件 ID 只代表接受发送，不代表进收件箱或邮箱已验证。可通过验签 webhook 记录 delivered/bounced/complained 等事件；使用原始 body 与 `svix-id/timestamp/signature`，去重并防重放，成功送达事件绝不能激活账号。[回调验签说明](https://resend.com/docs/webhooks/verify-webhooks-requests)。
9. 事务邮件关闭不必要的点击/打开追踪。日志只记 challenge ID、供应商 ID、错误类别及脱敏地址；不记录密码、验证码、重置凭据和完整邮件正文。

建议配置：

```text
# 以下是后续实现拟用的配置，当前代码尚不读取
MAIL_MODE=disabled                 # disabled | test | resend
MAIL_FROM=糖包 <no-reply@account.example.com>
APP_ORIGIN=https://example.com
# Worker secrets：RESEND_API_KEY、EMAIL_CODE_PEPPER、MAIL_PAYLOAD_KEY
# 启用 webhook 再添加 RESEND_WEBHOOK_SECRET
```

拟定 API：`POST /api/auth/register`、`/login`、`/logout`、`/email/verify`、`/email/resend`、`/password/forgot`、`/password/reset`；`GET /api/auth/me`；`POST /api/account/legacy-claims` 及其确认接口。邮箱/密码等都不放 query string。详细请求/响应契约在对应 Issue 实现前确定。

发送量估算：`新注册验证 + 验证重发 + 找回请求/重发 + 后续改邮箱验证`，普通登录约为 0 封。先查当前账户配额、设置全站预算/告警再上线；本文不假定某个免费套餐额度，也不执行真实群发。预算耗尽时说明“暂时无法发送，请稍后重试”，不能显示“已发到邮箱”。

## 验证和上线门槛

使用合成数据和邮件 mock 验证：匿名首段并发/超时重试/删除不返还、第二段草稿保留、注册重复邮箱、密码错误限流、过期/错误/重放验证码、找回后的会话撤销、普通登录零邮件、旧口令重复/并发认领、其他模型越权、账号/模型停用、迁移回退。D1 与 Turso 分别记结果。

真实邮件验证单独使用运营方指定的受控地址，检查收到验证码、垃圾箱、过期、送达/退信回调及额度；mock、API 接受、收件箱送达与业务验证成功是四个不同结论。公开部署前更新隐私文案，说明邮箱、账号、验证记录、Resend 送信和保留/删除规则。

实施前仍需确认：未验证账号的聊天权限、一个账号可拥有的模型数量、旧用户迁移窗口/争议核验方式、发信域名与当前 Resend 账户预算，以及 Worker 密码 KDF 的基准结果。除这些边界外，可先按已确认的产品规则拆分实现。
