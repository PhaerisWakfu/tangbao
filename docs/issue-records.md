# Issue 记录格式

供 requirement、develop、bugfix 三个 Skill 共用，按任务删减。空字段写“未执行/待确认”并说明影响，不用占位文字冒充已完成。项目规范以当前 checkout 的 [Issue 工作流程](issue-workflow.md) 为准。

## 需求或技术任务

```markdown
阶段：待澄清 / 待开发 / 开发中 / 待验证 / 待验收
优先级：P0–P3，说明理由

## 用户与结果
谁在什么场景遇到什么问题，希望获得什么可观察结果。

## 范围与决定
已确认规则：……
本次范围及不做项：……
实施建议及未决问题：……

## 验收
- [ ] 正常结果
- [ ] 异常和权限边界
- [ ] 数据/兼容影响（适用时）

## 方案与依赖
涉及的页面、接口、存储及共享消费者；先决依赖及迁移/补偿方式。
父项与依赖分别注明；另行设置并核验原生父子关系。

## 验证计划
本地合成步骤、自动检查和需要浏览器/外部环境确认的结果。

## 工作位置与交付
分支、基线；实现/验证/提交/部署/验收分别记录。
```

技术 Task 也要说明其服务的用户/工程结果。阶段与优先级在主描述维护；未配置的状态标签、Projects、原生 Issue type 不写成已启用。

## Epic 拆分

父项保留总体结果、范围、总体验收、分支/基线和交付顺序。子项各有独立的验收及影响范围，用 GitHub 原生层级关联。仅跨任务复用的依赖保留为依赖；不要为了凑层级创建同义父子任务。

标题无需机械带前缀。分类与责任人必须读取实际元数据确认，不能从正文或标题推断。

## Bug 调查补充

```markdown
证据级别：静态发现 / 本地合成复现 / 指定真实环境复现 / 待复现
环境与版本：分支、commit、dirty 状态；本地 instance（适用时）
触发步骤：最小必要步骤及前置条件
预期：……
实际：……
影响：……
根因：证据支持的结论；未证实则写假设
修复方案：拥有该规则的代码、共享消费者、数据修复是否另行处理
回归：原触发场景、相邻路径、错误恢复、权限边界
```

公开安全 Bug 不使用以上格式展开利用步骤，转按仓库安全规则脱敏。

## 本轮交付记录

```markdown
实现：实际变化及影响；未做的范围。
验证：在哪个分支/commit/dirty 状态和环境，做了什么，得到什么结果。
失败/未验证：保留有意义的首次失败、重跑条件，以及未覆盖的后端/浏览器/供应商。
提交：未提交 / SHA；推送：未推送 / 已核对目标；PR：链接（适用时）。
部署：未部署 / 环境与版本、回滚点。
验收：未验收 / 验收人和证据。
遗留：对应 Issue；必要依赖、阻碍与下一步。
```

只引用合成步骤和脱敏证据。截图、日志及凭据留在忽略目录；真实邮件 API 接受、邮箱送达和业务验证成功分别记结论。文档或 Skill 交付无需为了填表部署业务站点。
