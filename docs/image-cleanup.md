# 图片删除与失败重试

对应 [#12](https://github.com/PhaerisWakfu/tangbao/issues/12)。本机制处理删除整段对话时的图片关联和文件清理，不包含历史孤儿回收或上传失败补偿。

## 删除行为

服务端先核对对话权限，再在同一数据库事务中：

1. 将本对话的图片 key 写入 `image_cleanup_jobs`。
2. 删除图片关联记录、消息和对话。

事务提交后，对话即删除成功，图片接口也不能再通过已删除的消息读取文件。服务端立即尝试清理这段对话的文件；KV 临时失败或清理结果确认失败，都保留数据库中的任务，不把已经完成的对话删除显示为失败。

数据库事务失败时，待清理任务和对话数据一起回滚，不删除文件。待清理任务没有指向原对话的外键，原记录消失后仍可独立执行。

## 后台恢复与资源边界

复用现有每分钟 Cron，不增加独立调度。每次最多处理 20 个到期任务；即时清理也只处理本对话最多 20 个任务，剩余由 Cron 接续。查询使用到期时间和对话索引，避免在普通聊天请求中扫描队列。

失败后依次等待约 1、2、4、8、16、32、60 分钟，之后每次至少等待 60 分钟再试，失败任务持续保留。恢复时间还受调度和积压量影响。每个任务尝试一次 KV 删除，并写入删除确认或下次重试时间；没有任务时，新增的清理调度只有一次索引查询。

KV 删除成功后才移除任务；确认写入失败时，下一次再次删除同一个 key。图片 key 不复用，删除操作可重复，因此重复调度或重启后重试不会删除其他对话的图片。进程内状态不承担任务持久化。

日志事件 `image_cleanup_retry` 表示某个任务未完成，`image_cleanup_deferred` 表示本次即时清理未能执行完；任务表中的 `attempts` 和 `next_attempt_at` 可用于维护者核对积压，不公开给普通用户。维护模式沿用现有规则暂停定时处理，恢复后继续。

## 迁移与回退

部署新代码前，先按获授权环境的迁移流程应用 `0023_image_cleanup_jobs.sql`。本地隔离实例的 `local:prepare` / `local:verify` 会自动应用并核验全部迁移。

迁移只新增表和索引，不扫描或删除旧图片。它不能恢复早先已经失去关联的历史文件，也不会自动清理原有孤儿记录。

回退代码时保留任务表和其中的数据；旧代码不处理这些任务，需要重新启用本清理器后继续处理。不要为了回退而丢弃未完成的文件 key。运行代码前必须有该表，不能依赖请求入口自动建表。

## 本地验证

```sh
node --test scripts/image-cleanup.test.mjs
npm run local:verify
```

定向测试使用本地 libSQL、当前实际数据库适配器和业务函数，以及可注入故障的内存文件替身，覆盖事务回滚、失败退避、处理器重新加载、确认丢失、分批和重复调度。只加载相关表结构，不代表全量 Turso 迁移或远程供应商验收。正式 HTTP、D1/KV 和定时恢复验证的结果记录在 Issue；浏览器、生产 Cron 与云端迁移分别验收。
